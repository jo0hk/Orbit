## 0. 이 문서가 정하는 것

1학기 4단계 탐사 미션을 **센서로 판정 가능한 형태**로 재작성했습니다.
"사용자가 산책을 했다" 같은 조건은 구현할 수 없으므로, 전부 **이벤트 + 임계값 + 시간창**으로 환산했습니다.

> ⚠️ 원본 `오빗_미션리스트.hwpx`는 노션 첨부 파일이라 읽지 못했습니다. 초안 4단계와 1학기 페르소나에 남은 언급("3단계 탐사 미션(바깥 산책)")을 근거로 작성했으므로, **원본과 단계 구성이 맞는지 확인이 필요합니다.**

## 1. 미션 상태 전이

```
              제안
   (없음) ──────────▶ PROPOSED ──첫 이벤트──▶ IN_PROGRESS
                         │                        │
                         │                        ├─조건 충족─▶ SUCCESS
                         │                        │
                         ├─거부 발화──▶ DEFERRED  └─시간 초과─▶ TIMEOUT
```

| 상태 | 의미 | 오빗 반응 |
| --- | --- | --- |
| `PROPOSED` | 제안했고 대기 중 | 제안 대사 |
| `IN_PROGRESS` | 첫 관련 이벤트 수신 | 없음 |
| `SUCCESS` | 성공 조건 충족 | 성공 대사 |
| `TIMEOUT` | 시간 초과 | 재시도 대사 |
| `DEFERRED` | 사용자가 거부 | 예외 대화 1번 (실내 대체 미션 제안) |

### ⚠️ `FAILED` 상태를 두지 않습니다

3주차 예외 대화 원칙과 충돌하기 때문입니다. 산책을 안 했다고 실패 판정을 내리면 **강요하는 서비스**가 됩니다. 조건 미달은 전부 `TIMEOUT`(유예) 또는 `DEFERRED`(보류)로 기록하고, 재시도 대사는 압박 없는 톤을 씁니다.

### 재제안 쿨다운

같은 미션을 `TIMEOUT` / `DEFERRED` 처리한 뒤 **최소 3시간** 동안 재제안하지 않습니다. 하루 최대 제안 횟수는 미션당 **2회**입니다.

## 2. 미션 정의

### M1. 교신 응답 — `m_touch_ack`

| 항목 | 값 |
| --- | --- |
| 단계 | 1단계 |
| 센서 | 터치 |
| 성공 조건 | **첫 터치 시각 기준 2,000 ms 이내에 터치 3회** |
| 타임아웃 | 제안 후 60초간 터치 이벤트 없음 |
| 선행 조건 | 없음 (언제든 제안 가능) |

**판정 기준점은 제안 시각이 아니라 첫 터치 시각입니다.** 사용자가 언제 시작할지 알 수 없기 때문입니다.

> ⚠️ **HW 확인 필요** — 터치 센서 디바운스 간격. 채터링이 걸러지지 않으면 한 번 누른 것이 3회로 잡혀 미션이 즉시 완료됩니다. **최소 50 ms 디바운스**를 권장합니다.

### M2. 기지 환기 — `m_light_vent`

| 항목 | 값 |
| --- | --- |
| 단계 | 2단계 |
| 센서 | 조도 |
| 선행 조건 | 제안 시점 조도 **≤ 50 lux** |
| 성공 조건 | 제안 후 10분 이내에 조도 **≥ 200 lux 가 연속 30초 유지** |
| 타임아웃 | 10분 |

**30초 유지 조건이 필요한 이유**: 손전등이나 휴대폰 화면이 순간적으로 스치는 것을 성공으로 오판하지 않기 위함입니다.

> 📌 **조명을 켠 것과 창문을 연 것은 센서로 구분할 수 없습니다.** 대사를 "광량 확보"로 포괄해 어느 쪽이든 자연스럽게 읽히도록 했습니다.

> ⚠️ **HW 확인 필요** — 조도 센서 실측 범위. 50/200 lux는 일반값 기준이므로, 실내 야간·주간·조명 on 상태를 측정해 조정해야 합니다.

### M3. 기상 점검 — `m_accel_wake`

| 항목 | 값 |
| --- | --- |
| 단계 | 3단계 |
| 센서 | 가속도 |
| 성공 조건 | 가속도 크기가 임계 이상인 샘플이 **3초 구간의 60% 이상** |
| 타임아웃 | 제안 후 5분 |
| 배타 조건 | **탐사 세션(M4) 활성 중에는 제안·판정하지 않음** |

**배타 조건이 필요한 이유**: 걷는 동안 가속도 임계를 계속 넘기 때문에, M4 수행 중이면 M3가 저절로 완료돼 버립니다.

> ⚠️ **HW 실측 필요 — 임계값 미확정**
>
> 제안값: `| |a| − 1g | ≥ 0.8g`
>
> 측정 절차를 권합니다.
> 1. 키링을 책상에 둔 상태 (정지) — 노이즈 상한 확인
> 2. 주머니에 넣고 평보 30초 — 걷기 피크 확인
> 3. 손에 쥐고 흔들기 5초 — 목표 동작 하한 확인
>
> **걷기 피크와 흔들기 하한 사이**에 임계를 잡습니다.

### M4. 외부 정찰 — `m_gps_scout`

| 항목 | 값 |
| --- | --- |
| 단계 | 4단계 |
| 센서 | GPS (앱) |
| 성공 조건 | 탐사 세션 시작 후 **누적 이동 거리 ≥ 300 m** |
| 타임아웃 | 없음 (세션 종료 시 판정) |
| 미달 시 | `TIMEOUT` 으로 기록하되 **이동 거리를 부분 달성으로 저장** |
| 활성 시점 | **7주차 GPS 연동 이후** |

> ⚠️ **거리 누적 규칙 — 앱 파트 확인 필요**
>
> - 연속 샘플 간 거리가 **5 m 미만이면 무시** — 정지 상태 GPS 드리프트가 누적되는 것을 막습니다
> - 구간 속도가 **10 km/h 초과면 제외** — 차량·대중교통 이동을 산책으로 집계하지 않습니다
>
> 두 규칙은 8주차 "탐사 데이터 유효성 검증"의 선행 조건입니다.

## 3. MQTT 이벤트 매핑

현재 페이로드는 평문 문자열(`TOUCHED`, `FUEL_UP` 등)이라 **값과 시각이 없어 위 조건을 판정할 수 없습니다.** 1주차 인터페이스 정의서에서 제안한 JSON 형식이 전제입니다.

```json
{ "type": "TOUCH", "user_id": 1, "value": 1,    "ts": 1758387600000 }
{ "type": "LUX",   "user_id": 1, "value": 15,   "ts": 1758387600000 }
{ "type": "ACCEL", "user_id": 1, "value": 2.41, "ts": 1758387600000 }
```

| `type` | `value` 의미 | 쓰이는 미션 | 전송 시점 |
| --- | --- | --- | --- |
| `TOUCH` | 터치 1회 (항상 `1`) | M1 | 이벤트 발생 시 |
| `LUX` | 조도 (lux) | M2 | 5초 주기 + 변화량 50 이상일 때 |
| `ACCEL` | 가속도 크기 (g) | M3 | 미션 활성 중 10 Hz |

> `ts`는 **HW가 찍는 밀리초 단위 epoch**입니다. 서버 수신 시각을 쓰면 네트워크 지연이 시간창 판정을 왜곡합니다.

### 기존 이벤트는 유지

`FUEL_UP` / `LOVE_UP` / `STAGE_UP` / `JACKPOT_SUCCESS` / `EMOTION_*` 는 캐릭터 스탯용이므로 **그대로 둡니다.** 미션 판정용 JSON 채널을 별도로 추가하는 방식입니다.

## 4. 중복 처리 (6주차 선행)

- 미션 1회 제안마다 `mission_instance_id` 를 발급합니다
- 이미 `SUCCESS` 인 인스턴스에 이벤트가 더 들어와도 **재처리하지 않습니다**
- 동일 `(type, ts)` 이벤트가 중복 수신되면 무시합니다
- 성공 대사는 **인스턴스당 정확히 한 번만** 출력합니다

> 6주차 검증 항목 "중복 이벤트로 미션이 두 번 완료될 때 오빗이 칭찬을 두 번 하지 않는지"가 이 규칙으로 커버됩니다.

## 5. 성공 시 연동

미션이 `SUCCESS` 가 되면 백엔드는 다음을 수행합니다.

| 대상 | 처리 |
| --- | --- |
| `orbit_mood` | **`HAPPY` 로 변경** (1주차 감정 분리안) |
| `CharacterStatus` | 기존 스탯 로직대로 연료·친밀도 증가 |
| 대화 로그 | `missionId`, `missionResult=success` 기록 |
| AI 서버 | 다음 요청의 `mission_id` / `mission_result` 에 실어 전달 |

**감정 모델 재학습 없이 오빗이 기뻐할 수 있는 경로**가 이것입니다. 사용자 감정(`user_emotion`)은 5클래스 그대로 두고, 미션 성공은 `orbit_mood` 를 움직입니다.

## 6. 하드웨어 신호

값은 1주차 확정 enum(`ai/app/schemas.py`)만 사용합니다.

| 상황 | `led` | `vibe` | `oled_expression` |
| --- | --- | --- | --- |
| 미션 제안 | *현재 감정 매핑을 따름* | *동일* | *동일* |
| **SUCCESS** | `rainbow` | `strong_double` | `star_eyes` |
| **TIMEOUT** (재시도 유도) | `dim_blue` | `short` | `idle_eyes` |
| **DEFERRED** (거부) | `dim_blue` | `soft_continuous` | `idle_eyes` |

**제안 시점에 미션 전용 신호를 쓰지 않는 이유**: 미션 제안은 일반 대화 흐름 안에서 나오므로, 그 순간의 사용자 감정에 맞추는 편이 자연스럽습니다.
