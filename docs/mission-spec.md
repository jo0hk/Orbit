## 0. 원본과의 관계

1학기 기획서에는 **4단계 × 20개 = 80개 미션**이 정의되어 있습니다.

| 단계 | 이름 | 성격 |
| --- | --- | --- |
| 1 | 시스템 점검 | 방 안. 자기 돌봄 |
| 2 | 감각의 깨움 | 창을 열고 경계 확장 |
| 3 | 행성 표면 탐사 | 실제 외출과 산책 |
| 4 | 현지인과 교신 | 사회 복귀 |

2학기 과제는 "실제 구현 가능한 미션 중심으로 정리"이므로, **80개 전부가 아니라 현재 하드웨어로 판정 가능한 5개를 골랐습니다.**

### 선정 기준

1. 현재 하드웨어(터치·조도·가속도)와 앱 GPS로 판정 가능할 것
2. **각 단계를 최소 1개씩 대표할 것** — 은둔에서 사회 복귀로 이어지는 서사가 끊기면 10주차 시연에서 이야기가 무너집니다
3. 판정 조건이 임계값 + 시간창으로 환산 가능할 것

**단계 구성과 미션 명칭은 원본을 그대로 따릅니다.**

### 원본이 전제하지만 현재 없는 센서

원본 80개 중 상당수가 아래를 요구합니다. 나머지 75개를 살리려면 이 중 일부가 필요합니다.

| 센서 | 원본에서 쓰이는 곳 | 현재 |
| --- | --- | --- |
| 마이크 (센서로서) | 호흡음, 주변 소음, 바람 소리, 노래 | 음성 교신용으로만 존재 |
| 자이로 | 수평 감지, 회전 궤적 | 없음 |
| 기압 | 고도 변화 | 없음 |
| 온도 · 습도 | 거주 환경 | 없음 |
| 충전 전압 감지 | 에너지 커넥트 | 미확인 |
| 앱 카메라 · OCR | 사진 인증, 홍보물 인식 | Vision AI는 있으나 미연동 |

## 1. 미션 상태 전이

```
              제안
   (없음) ──────────▶ PROPOSED ──첫 이벤트──▶ IN_PROGRESS
                         │                        │
                         │                        ├─조건 충족─▶ SUCCESS
                         │                        │
                         ├─거부 발화──▶ DEFERRED  └─시간 초과─▶ TIMEOUT
```

### ⚠️ `FAILED` 상태를 두지 않습니다

3주차 예외 대화 원칙과 충돌하기 때문입니다. 산책을 안 했다고 실패 판정을 내리면 **강요하는 서비스**가 됩니다. 조건 미달은 전부 `TIMEOUT`(유예) 또는 `DEFERRED`(보류)로 기록합니다.

### 재제안 쿨다운

`TIMEOUT` / `DEFERRED` 후 **최소 3시간**, 하루 최대 제안은 미션당 **2회**입니다.

## 2. 미션 정의

### M1. 아침 온기 나누기 — `m_warm_touch` · 1단계

> 원본 미션 내용: 잠에서 깨어 키링을 손바닥으로 3초간 가볍게 감싸 쥐기
> 원본 검증 방법: 터치 센서가 3초 이상 연속 신호 감지

| 항목 | 값 |
| --- | --- |
| 센서 | 터치 |
| 성공 조건 | **터치 신호가 3초 이상 연속 유지** |
| 타임아웃 | 120초 |

**연속 유지 판정이라 횟수 카운트보다 오탐이 적습니다.** 디바운스 문제도 발생하지 않습니다.

> ⚠️ **HW 확인** — 손에 쥔 상태에서 정전용량 변화가 3초간 안정적으로 잡히는지. 중간에 신호가 끊기면 타이머를 리셋할지, 짧은 끊김(200ms 이하)은 허용할지 정해야 합니다.

### M2. 엔진 시동 인사 — `m_engine_start` · 1단계

> 원본 미션 내용: 캐릭터의 머리 부분을 두 번 톡톡 두드려 깨우기
> 원본 검증 방법: 가속도 센서가 짧고 강한 충격 2회 감지

| 항목 | 값 |
| --- | --- |
| 센서 | 가속도 |
| 성공 조건 | **짧고 강한 충격 2회** (간격 300~1500 ms) |
| 타임아웃 | 300초 |

**충격 패턴은 걷기와 구분이 쉽습니다.** 흔들기(원본 '궤도 회전 테스트')보다 판정이 안정적이라 이쪽을 택했습니다.

> ⚠️ **HW 실측 필요** — 충격 임계값과 2회 간격 범위. ①정지 ②평보 30초 ③두드리기 를 측정해 걷기 피크보다 위에서 임계를 잡습니다.

### M3. 태양광 패널 전면 개방 — `m_solar_panel` · 2단계

> 원본 미션 내용: 커튼을 끝까지 열고 방 안으로 햇빛 들이기
> 원본 검증 방법: 조도 센서가 낮은 수치에서 급격히 상승하여 일정 시간 유지

| 항목 | 값 |
| --- | --- |
| 센서 | 조도 |
| 선행 조건 | 제안 시점 조도 **≤ 50 lux** |
| 성공 조건 | 10분 이내에 **≥ 200 lux 가 연속 30초 유지** |
| 타임아웃 | 10분 |

원본의 "일정 시간 유지"를 **30초**로 구체화했습니다. 손전등이나 휴대폰 화면이 순간적으로 스치는 것을 성공으로 오판하지 않기 위함입니다.

> 📌 커튼을 연 것과 전등을 켠 것은 센서로 구분할 수 없습니다. 원본 1단계 '태양광 패널 점검'(전등 켜기)과 사실상 같은 판정이 됩니다.

> ⚠️ **HW 실측 필요** — 50/200 lux는 일반값입니다. 실내 주간·야간·조명 on 을 측정해 보정하세요.

### M4. 베이스캠프 반경 확보 — `m_basecamp_100m` · 3단계

> 원본 미션 내용: 집 건물 입구에서 100m 정도 떨어진 지점까지 천천히 걸어갔다 오기
> 원본 검증 방법: 핸드폰 GPS 기반 이동 거리 측정 (실시간 지도 트래킹)

| 항목 | 값 |
| --- | --- |
| 센서 | GPS (앱) |
| 성공 조건 | 집 출발 후 **누적 이동 거리 ≥ 100 m** |
| 타임아웃 | 없음 (세션 종료 시 판정) |
| 미달 시 | `TIMEOUT` 기록 + 이동 거리를 부분 달성으로 저장 |
| 활성 시점 | **7주차 GPS 연동 이후** |

> ⚠️ **앱 확인 필요 — 거리 누적 규칙**
>
> - 연속 샘플 간 거리 **5 m 미만 무시** — 정지 상태 드리프트 누적 방지
> - 구간 속도 **10 km/h 초과 제외** — 차량·대중교통을 산책으로 집계하지 않음
>
> **100 m 는 GPS 오차(±10 m)와 가까워** 드리프트 필터가 특히 중요합니다. 필터 없이 실내에 가만히 있어도 수십 m 가 누적될 수 있습니다.

### M5. 첫 번째 외교적 수사 — `m_first_greeting` · 4단계

> 원본 미션 내용: 편의점이나 카페에서 점원에게 "안녕하세요"라고 명확하게 인사하기
> 원본 검증 방법: 마이크 센서 및 STT로 인사말 키워드 추출

| 항목 | 값 |
| --- | --- |
| 센서 | **자가 보고** (앱 미션 완료 버튼) |
| 성공 조건 | 사용자가 앱에서 완료 보고 |
| 활성 시점 | 앱 버튼 구현 이후 |

### 🔴 원본 검증 방법을 채택하지 않았습니다

원본은 **상시 마이크 청취 + STT**를 전제합니다. 점원에게 건네는 인사를 감지하려면 마이크가 계속 켜져 있어야 합니다.

- 사용자 본인뿐 아니라 **대화 상대(점원)의 음성까지 동의 없이 수집**됩니다
- 3주차에 대화 암호화·비식별 처리를 설계한 서비스가 상시 청취를 하는 것은 앞뒤가 맞지 않습니다

**자가 보고로 대체**했습니다. 4단계 서사를 유지하면서 이 문제를 피하는 유일한 방법입니다. 4단계 미션 대부분(주문하기, 길 묻기, 칭찬 건네기)이 같은 문제를 갖고 있으므로, **4단계 전체를 자가 보고 기반으로 설계**하시길 권합니다.

## 3. MQTT 이벤트 매핑

현재 페이로드는 평문 문자열(`TOUCHED`, `FUEL_UP` 등)이라 **값과 시각이 없어 위 조건을 하나도 판정할 수 없습니다.**

```json
{ "type": "TOUCH", "user_id": 1, "value": 1,    "ts": 1758387600000 }
{ "type": "LUX",   "user_id": 1, "value": 15,   "ts": 1758387600000 }
{ "type": "ACCEL", "user_id": 1, "value": 2.41, "ts": 1758387600000 }
```

| `type` | `value` 의미 | 쓰이는 미션 | 전송 시점 |
| --- | --- | --- | --- |
| `TOUCH` | `1` = 접촉 중, `0` = 해제 | M1 | 상태 변화 시 (연속 유지 판정용) |
| `LUX` | 조도 (lux) | M3 | 5초 주기 + 변화량 50 이상일 때 |
| `ACCEL` | 가속도 크기 (g) | M2 | 미션 활성 중 10 Hz |

> M1은 **연속 유지**를 판정하므로 `TOUCH` 가 접촉 시작·해제 두 시점 모두 전송되어야 합니다. 기존 `TOUCHED` 처럼 단발 신호만 오면 3초 유지를 알 수 없습니다.

> `ts`는 **HW가 찍는 밀리초 epoch**입니다. 서버 수신 시각을 쓰면 네트워크 지연이 시간창 판정을 왜곡합니다.

기존 `FUEL_UP` / `LOVE_UP` / `EMOTION_*` 등 스탯 이벤트는 **그대로 둡니다.**

## 4. 중복 처리 (6주차 선행)

- 미션 1회 제안마다 `mission_instance_id` 발급
- 이미 `SUCCESS` 인 인스턴스는 **재처리하지 않음**
- 동일 `(type, ts)` 이벤트 중복 수신 시 무시
- 성공 대사는 **인스턴스당 정확히 한 번**

## 6. 하드웨어 신호

1주차 확정 enum(`ai/app/schemas.py`)만 사용합니다.

| 상황 | `led` | `vibe` | `oled_expression` |
| --- | --- | --- | --- |
| 미션 제안 | *현재 감정 매핑을 따름* | *동일* | *동일* |
| **SUCCESS** | `rainbow` | `strong_double` | `star_eyes` |
| **TIMEOUT** | `dim_blue` | `short` | `idle_eyes` |
| **DEFERRED** | `dim_blue` | `soft_continuous` | `idle_eyes` |

> 원본은 미션마다 개별 LED 연출을 지정합니다(노란색 회전, 하트 모양, 물방울 애니메이션 등). 현재 enum 4종으로는 표현할 수 없으므로 상황 단위로 단순화했습니다. HW가 연출을 확장할 수 있다면 enum을 늘리는 쪽을 검토하세요.

### 8번 — 표기 불일치

| 출처 | 표기 |
| --- | --- |
| 1학기 페르소나 설정안 (노션) | `치칙-` |
| 1학기 미션리스트 (원본) | `치칙-` / `칙-` |
| 1학기 실제 프롬프트 (`ContextInjector`) | `치직-` |
| 현재 레포 전체 | `치직-` |

**기획 문서는 `치칙-`, 구현은 `치직-`입니다.** 현재는 구현 쪽으로 통일해 두었으나, 기획 의도가 `치칙-`이라면 바꾸는 편이 맞습니다. 프롬프트·대사·테스트를 한 번에 치환하면 되는 작업입니다.
