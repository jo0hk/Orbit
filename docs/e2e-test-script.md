# E2E 테스트 대본 — 대표 미션 2종 (2학기 5주차)

> 작성: AI/PM · 2026-09-28 · **개정 2026-10-01** (09-17 회의 결정 반영)
> 진행: PM · 참여: HW · 백엔드 · 앱 · AI
> 선행 문서: `docs/stage-mission-judgement.md` · `docs/mission-context-injection.md`

사용자 입력 → AI 서버 판정 → 백엔드 미션 완료·단계 상승 → 오빗 응답·HW 신호까지 **한 바퀴를 실제로 도는지** 확인합니다. 이번 대본의 결과가 6주차 회귀 테스트 세트의 첫 케이스가 됩니다.

> **10-01 개정 사항.** 초판은 4주차 센서 미션(M1 아침 온기 나누기 · M3 태양광 패널 개방)을 대표 미션으로 골랐으나, 두 미션은 09-17 회의에서 확정한 미션 목록(백엔드 DB)에 없습니다. 대표 미션을 **1단계 기분 텍스트 · 2단계 날씨 음성 보고**로 바꾸고, MQTT 센서 판정 전제를 AI 서버 판정 전제로, HW 신호를 공통 제어값으로 교체했습니다.

## 1. 대표 미션 선정

### 선정: 1단계 기분 텍스트 (`EMOTION_TEXT`) · 2단계 날씨 음성 보고 (`WEATHER_VOICE`)

| 미션 | 선정 이유 |
| --- | --- |
| **1단계 앱 대화창에 오늘 기분 단어로 입력하기** | 판정이 가장 단순한 경로입니다(텍스트 + 키워드 규칙). 음성·사진 없이 **AI 서버 판정 → 결과 API → 백엔드 완료·단계 상승**이 도는지 먼저 확인하는 기준 케이스입니다 |
| **2단계 창밖 날씨를 보고 오빗에게 음성으로 보고하기** | 키링 음성 → STT → 판정 → 응답 음성·HW 신호까지 **전 구간**을 지납니다. 날씨 API 값과 비교하는 판정이라 Context API 연동도 함께 검증합니다 |

두 미션이 1단계 → 2단계로 이어지므로 **은둔 → 감각의 깨움** 서사가 시연에서 자연스럽게 연결되고, 성공 시 단계 상승(백엔드)까지 이어서 보여줄 수 있습니다.

### 제외

| 미션 | 이유 |
| --- | --- |
| 3단계 랜드마크 사진 | 사진 업로드 경로(앱 → AI 서버) 미정. 8주차 야외 사진 판정 검증과 함께 |
| 4단계 대중교통 | 야외 이동 필요. 7~8주차 야외 테스트에서 |

## 2. 사전 조건 — 하나라도 안 되면 테스트를 시작하지 않습니다

| # | 항목 | 담당 | 확인 방법 |
| --- | --- | --- | --- |
| P1 | 백엔드 Context API — 오늘 미션 `{missionId, stage, missionType, status}` 와 날씨 범주 포함 | 백엔드 | Postman으로 테스트 사용자 조회 |
| P2 | 백엔드 결과 API `POST /api/missions/{missionId}/result` | 백엔드 | 구현 완료 (5주차). `confidence` / `reason` 필드는 선택 |
| P3 | AI 서버 1·2단계 규칙 판정 + 결과 API 호출 | AI | 단위 테스트 통과 |
| P4 | AI 서버 앱 텍스트 교신 엔드포인트 | AI | 1단계용. 현재는 음성 엔드포인트만 있음 |
| P5 | 테스트 사용자 2명 — **사용자 A: 1단계**, **사용자 B: 2단계**, 각자 캐릭터·기기 매핑 | 백엔드 | 아래 참조 |
| P6 | 날씨 고정 수단 — 테스트 중 Context API가 지정한 날씨 범주를 반환 | 백엔드 | 실제 날씨에 따라 결과가 바뀌면 재현 불가 |
| P7 | `GEMINI_API_KEY` 설정 | AI | 테스트 전에 요청을 한 번 보내 `fallback_triggered=false` 인지. 키는 첫 LLM 호출 때 확인되므로 기동 로그로는 알 수 없음 |
| P8 | 키링 음성 업로드 (녹음 → AI 서버) | HW | 2단계용. 미구현이면 **녹음 파일을 Postman으로 직접 업로드**하고 HW 신호는 응답 JSON으로만 확인 |
| P9 | `applyHardwareAction` 에 `EXPR_HAPPY` 분기 | HW | 시리얼 `h` 입력 시 웃는 표정이 나오는지 |

> **P5 — 사용자를 둘로 나누는 이유:** 백엔드는 하루에 미션을 1개만 배정합니다(`user_id`, `assigned_date` 고유). 사용자 A가 1단계를 성공해 단계가 2로 올라도 2단계 미션은 다음날에야 배정됩니다. 같은 날 2단계를 테스트하려면 처음부터 2단계인 사용자 B가 필요합니다.

## 4. 합격 기준

대사는 LLM이 생성하므로 **문장 일치가 아니라 규칙 충족**으로 판정합니다.

### 모든 AI 응답 공통

| # | 기준 |
| --- | --- |
| S1 | `speech` 공백 포함 **45자 이하** |
| S2 | `치직-` 포함 (위치 무관 — 페르소나는 첫머리를 요구하지 않음) |
| S3 | 끝의 마침표를 빼고 `오버` / `라저` / `교신 종료` 중 하나로 끝남 |
| S4 | `실패` 라는 단어가 없음 |
| S5 | `fallback_triggered = false` |

### 결과별

| 결과 | 대사 기준 | `oled` | `led` | `vibe` | 백엔드 상태 |
| --- | --- | --- | --- | --- | --- |
| 성공 | 미션 키워드 1개 이상 (1단계: 기분·마음·상태·신호 / 2단계: 날씨·하늘·관측·맑·비·구름) · 느낌표 ≤ 1 | `EXPR_HAPPY` | `rainbow` | `strong_double` | `COMPLETED`, stage +1 |
| 조건 미달 | 재촉어(빨리·꼭·반드시·다시 해야) 없음 | `EXPR_NORMAL` | `blue` | `short_pulse` | `IN_PROGRESS` 유지 |
| 거부 (보류) | 같은 미션 재권유 없음 · `아쉽` 없음 | `EXPR_NORMAL` | `blue` | `soft_continuous` | `IN_PROGRESS` 유지, **결과 API 호출 없음** |

### 판정 로그

AI 서버 로그의 판정 사유 코드가 케이스별 기대 코드와 같아야 합니다(`stage-mission-judgement.md` 3절). 대사가 기준을 통과해도 코드가 다르면 불합격입니다. 판정이 맞았는데 대사만 우연히 맞은 경우를 걸러내기 위함입니다.

### 시간

| 구간 | 기준 | 비고 |
| --- | --- | --- |
| 입력 종료 → 오빗 응답 | **기록만** | 4주차 기준선 15,448 ms(AI 서버 단독, 1회 표본)와 비교. 이번에는 Context API 조회와 판정이 더해지므로 `latency` 단계별 값을 함께 적음 |
| 응답 → 백엔드 상태 반영 | **5초 이내** | 결과 API는 백그라운드 호출이라 응답보다 늦을 수 있음 |

## 5. 시나리오 1 — 1단계 기분 텍스트 (사용자 A)

**초기 상태** 사용자 A 단계 1, 오늘 미션 배정 완료(`IN_PROGRESS`). 각 케이스 전에 백엔드 담당이 미션 상태를 `IN_PROGRESS` 로 되돌립니다(1-A 이후).

| 케이스 | 입력 (앱 텍스트) | 기대 사유 코드 | 기대 결과 | 확인 포인트 |
| --- | --- | --- | --- | --- |
| **1-A 성공** | `오늘 좀 피곤해` | `MOOD_OK` | 성공. 백엔드 `COMPLETED`, 단계 1 → 2 | 결과 API 호출 1회, 단계 상승 |
| **1-B 조건 미달 → 재시도** | ① `ㅇㅇ` ② `그냥 그래` | ① `MOOD_NONE` ② `MOOD_OK` | ① 조건 미달, `IN_PROGRESS` 유지 ② 성공 | ①의 재시도 대사에 재촉어 없음. 같은 날 두 번째 시도로 성공 |
| **1-C 부정 감정도 성공** | `너무 우울해` | `MOOD_OK` | 성공. 감정이 `sad` 로 나오면 온기형(E) 문형, 느낌표 없음 | **기분 내용으로 성패를 가르지 않는지** |
| **1-D 거부** | `오늘은 하기 싫어` | (판정 없음) | 예외 대화 1번 톤, 보류 문형. **결과 API 호출 없음** | 백엔드 로그에 결과 요청이 없어야 함 |
| **1-E 고위험 발화** | `죽고 싶어` | (판정 없음) | 고정 응답(무전 톤 아님). 결과 API 호출 없음. 미션 `IN_PROGRESS` 유지 | 미션보다 안전 대응이 우선 |
| **1-F 완료 후 재입력** | 1-A 직후 `기분 좋아` | (판정 없음) | 일반 대화 응답. 미션 언급·축하 없음, 결과 API 호출 없음 | **칭찬 중복 방지.** Context API가 `COMPLETED` 를 주므로 판정하지 않음 |

> **1-D와 "귀찮아"** — `귀찮` 은 기분 표현 사전(부정)에도 있고 예외 대화 1번의 거부 트리거에도 있습니다. 1단계에서는 **"귀찮아" 단독은 기분 표현(성공)**, "하기 싫어"·"안 할래"처럼 **행동을 거부하는 표현만 거부**로 봅니다(`stage-mission-judgement.md` 2절). 이 구분을 6주차 회귀 테스트에 케이스로 추가합니다.

## 6. 시나리오 2 — 2단계 날씨 음성 보고 (사용자 B)

**초기 상태** 사용자 B 단계 2, 오늘 미션 배정 완료(`IN_PROGRESS`). 백엔드 담당이 케이스마다 날씨 고정값을 설정합니다. 입력은 키링 녹음, 또는 P8 미구현 시 미리 녹음한 파일 업로드.

| 케이스 | 날씨 고정값 | 발화 (음성) | 기대 사유 코드 | 기대 결과 | 확인 포인트 |
| --- | --- | --- | --- | --- | --- |
| **2-A 일치** | `CLEAR` | `오늘 날씨 맑아` | `WEATHER_MATCH` | 성공. 키링 `EXPR_HAPPY` · `rainbow` · `strong_double`. 백엔드 단계 2 → 3 | 응답 음성과 HW 신호가 **동시에** 나오는지 |
| **2-B 인접** | `CLEAR` | `구름이 좀 꼈어` | `WEATHER_NEAR` | 성공 | 관찰이 API와 조금 달라도 인정하는지 |
| **2-C 정반대 → 재시도** | `CLEAR` | ① `비 와` ② `아 다시 보니 맑네` | ① `WEATHER_OPPOSITE` ② `WEATHER_MATCH` | ① 조건 미달, 키링 `EXPR_NORMAL` · `blue` · `short_pulse` ② 성공 | ①의 대사가 사용자를 탓하지 않고 "센서와 다르다"로 표현하는지 |
| **2-D 날씨 표현 없음** | `CLEAR` | `몰라` | `WEATHER_NONE` | 조건 미달 | 재시도 대사가 하늘이 어떤지 묻는지 |
| **2-E 날씨 API 장애** | (조회 실패로 설정) | `흐려` | `WEATHER_API_DOWN` | 성공 | API 장애가 사용자 불이익이 되지 않는지 |
| **2-F 가라앉은 감정** | `RAIN` | 낮고 느린 목소리로 `응… 비 오네` | `WEATHER_MATCH` | 성공. 감정이 `sad` 면 온기형(E), 느낌표 없음. HW는 성공 신호 그대로 | 감정 모델이 `sad` 를 내지 않으면 문형 검증은 건너뛰고 **감정 결과를 기록** (8주차 오분류 수집) |

> 2-C ①처럼 정반대로 보고한 경우는 날씨 고정값과 실제 창밖이 다를 때 테스트 환경에서 흔히 생깁니다. 대장님 역에게 **실제 창밖이 아니라 대본대로** 말하도록 미리 안내합니다.

> STT 신뢰도 0.5 미만(예외 대화 5번, 판정 안 함)도 판정 경로의 분기지만, 잡음 녹음을 재현하기 어려워 이번 대본에서 뺐습니다. 6주차 회귀 테스트에서 녹음 파일로 추가합니다.
