## 1. 판정표

| 단계 | 미션 | 입력 경로 | 성공 조건 | 판정 주체 | 판정 방식 |
| --- | --- | --- | --- | --- | --- |
| 1 | 앱 대화창에 오늘 기분 단어로 입력하기 | 앱 텍스트 → AI 서버 | 기분을 나타내는 한글 표현이 1개 이상 있는 텍스트 | AI 서버 (규칙) | 키워드 사전 |
| 2 | 창밖 날씨를 보고 오빗에게 음성으로 보고하기 | 키링 음성 → AI 서버 | 날씨 표현이 있고, 날씨 API 범주와 일치하거나 인접 | AI 서버 (규칙) | STT + 키워드 사전 + 날씨 API |
| 3 | 동네 랜드마크(건물, 조형물) 사진 찍기 | 앱 카메라 → AI 서버 | 야외에서 찍은 건물·조형물 사진 | AI 서버 (Vision) | Gemini Vision 구조화 출력 |
| 4 | 대중교통 이용해 세 정거장 이상 이동하기 | 앱 카메라 2회 + 촬영 위치 → AI 서버 | 승차·하차 인증 사진이 모두 인정되고, 시간차 5분 이상, 두 촬영 지점 거리 1km 이상 | AI 서버 (Vision + 규칙) | Gemini Vision + 시간·거리 계산 |

**판정 결과는 모두 AI 서버가 백엔드 결과 API로 보냅니다.** 1단계는 회의 표에서 "백엔드 (AI 보조)"였으나, 09-17 회의 안건 2·5에서 앱 텍스트도 AI 서버를 거치고 대화 저장도 AI 서버가 하기로 정했으므로 텍스트가 백엔드에 직접 오지 않습니다. 판정 경로를 하나로 맞추기 위해 1단계도 AI 서버가 규칙으로 판정해 보내는 것으로 조정합니다. **판정 규칙은 LLM이 아니라 코드로 고정**합니다(1·2·4단계의 계산 부분). 3·4단계의 사진 인식만 Vision 모델을 씁니다.

## 2. 단계별 상세

### 1단계 — 시스템 점검: 기분 단어 입력 (`EMOTION_TEXT`)

| 항목 | 값 |
| --- | --- |
| 트리거 | 오늘 미션이 1단계(`IN_PROGRESS`)인 상태에서 앱 `TEXT` 채널 발화 |
| 성공 | 공백 제거 후 1자 이상, 기분 표현 사전과 1개 이상 일치 |
| 실패(`success:false`) | 기분 표현이 없는 텍스트 (예: "ㅇㅇ", "뭐해", 기호만) |
| 판정 안 함 | 행동을 거부하는 표현("하기 싫어", "안 할래", "안 해") → 예외 대화 1번, 결과 API 호출 안 함 (보류) |
| 감정 분석 | **판정 조건이 아님.** 결과는 대화 저장에 `emotion`으로만 기록 |

> **"귀찮아"는 거부가 아니라 기분입니다.** `귀찮` 은 아래 기분 사전에도 있고 `ai/prompts/exceptions.md` 1번(탐사 거부)의 트리거에도 있습니다. 1단계에서는 "귀찮아" 단독은 기분 표현(성공)으로 보고, "하기 싫어"처럼 **행동을 거부하는 표현만** 거부로 봅니다. 기분을 묻는 미션에 "귀찮아"라고 답한 것은 기분을 말한 것이기 때문입니다.

**감정 내용으로 성패를 가르지 않습니다.** "우울해"도 "좋아"도 성공입니다. 이 미션의 목적은 자기 상태를 말로 꺼내 보는 것이고, 특정 기분을 요구하면 강요가 됩니다.

기분 표현 사전 (초안, 어간 기준):

| 범주 | 예 |
| --- | --- |
| 긍정 | 좋, 기쁘, 행복, 신나, 설레, 편안, 괜찮, 상쾌 |
| 부정 | 슬프, 우울, 힘들, 지치, 피곤, 짜증, 화나, 불안, 무섭, 외롭, 답답, 귀찮 |
| 중립 | 그냥, 보통, 무난, 멍하, 심심, 모르겠 |

> 텍스트만으로 감정을 분석하면 오디오 특징이 0으로 채워진 채 추론됩니다(`emotion.py`의 폴백 경로). 멀티모달로 학습한 모델이라 텍스트 단독 정확도는 측정된 적이 없습니다. 판정에 쓰지 않으므로 미션 성패에는 영향이 없습니다.

> **고위험 발화가 먼저입니다.** "죽고 싶어" 같은 입력은 기분 표현이기도 하지만 `safety.py`가 먼저 가로채 고정 응답을 내고, 미션 판정은 하지 않습니다.

### 2단계 — 감각의 깨움: 날씨 음성 보고 (`WEATHER_VOICE`)

| 항목 | 값 |
| --- | --- |
| 트리거 | 오늘 미션이 2단계인 상태에서 키링 `VOICE` 채널 발화 |
| 선행 조건 | `stt_confidence ≥ 0.5`. 미만이면 예외 대화 5번(되묻기), 판정 안 함 |
| 성공 | 날씨 표현 1개 이상 + 날씨 API 현재 범주와 **일치 또는 인접** |
| 실패(`success:false`) | 날씨 표현 없음, 또는 API 범주와 정반대 (예: 사용자 "비 와" / API 맑음) |
| 판정 안 함 | 날씨 API 조회 실패 → 날씨 표현만 있으면 성공 처리 (사용자 탓이 아님) |

날씨 범주와 사전:

| 범주 | 사용자 표현 | 인접 범주 |
| --- | --- | --- |
| `CLEAR` 맑음 | 맑, 화창, 해, 햇빛, 쨍 | `CLOUDS` |
| `CLOUDS` 흐림 | 흐리, 구름, 우중충 | `CLEAR`, `RAIN` |
| `RAIN` 비 | 비, 소나기, 빗방울, 우산 | `CLOUDS` |
| `SNOW` 눈 | 눈 오, 눈이, 함박눈 | `RAIN`, `CLOUDS` |
| `MIST` 안개 | 안개, 뿌옇, 미세먼지 | `CLOUDS` |

**인접 범주를 허용하는 이유:** 날씨 API는 지역 단위이고 갱신이 늦습니다. "구름 조금 낀 맑음"을 사용자가 "흐려"라고 보고하는 것은 관찰이 틀린 게 아닙니다. 창밖을 보고 말했다는 행동이 미션의 핵심이므로, 명백히 반대인 경우만 다시 보게 합니다.

> **필요한 데이터:** AI 서버가 사용자 위치의 현재 날씨를 알아야 합니다. 백엔드 Context API에 `weather`(범주) 필드를 넣거나, AI 서버가 비식별 위치(`location_coarse`)를 받아 날씨 API를 직접 조회해야 합니다. 백엔드와 정해야 합니다(4절).

### 3단계 — 행성 표면 탐사: 랜드마크 사진 (`LANDMARK_PHOTO`)

| 항목 | 값 |
| --- | --- |
| 트리거 | 앱 사진 미션 화면에서 **카메라로 촬영한** 사진 업로드 (갤러리 선택 불가) |
| 성공 | Vision 결과 `is_outdoor = true` 그리고 `subject ∈ {building, structure, sculpture, signboard}` 그리고 `confidence ≥ 0.6` |
| 실패(`success:false`) | 실내 사진, 피사체가 랜드마크가 아님, 신뢰도 미달 |
| 판정 안 함 | Vision 호출 실패 → 비상 프로토콜, 결과 API 호출 안 함 (다시 찍을 수 있음) |

Vision 구조화 출력 (판정용, 1학기 칭찬 엔진과 별도 호출):

```json
{"is_outdoor": true, "subject": "building", "people_prominent": false, "confidence": 0.82, "description": "붉은 벽돌 교회 건물"}
```

- `description`은 칭찬 대사 재료로만 씁니다(1학기 "벚꽃이 만개한 나무" 수준의 구체성).
- **갤러리 업로드를 막는 이유:** 예전 사진이나 인터넷 이미지로 미션을 통과할 수 있습니다. 화면을 다시 찍는 경우까지 막을 수는 없으며, MVP 한계로 기록합니다.
- **사람이 주 피사체인 사진(`people_prominent = true`)은 실패로 처리하고 사물을 찍도록 안내합니다.** 타인의 얼굴이 저장·전송되지 않게 하기 위함입니다. 사진 원본은 판정 후 저장하지 않고 판정 결과와 `description`만 남깁니다.

### 4단계 — 현지인과 교신: 대중교통 세 정거장 (`TRANSIT`)

09-17 회의에서 "GPS로 미세한 위치 판정이 어렵다"는 컨셉 발표 피드백에 대해 카메라 인증(하차벨·카드 단말기 촬영 등, AI 판정)으로 방향을 잡았습니다. 이를 **승차·하차 2회 촬영**으로 구체화합니다.

| 항목 | 값 |
| --- | --- |
| 승차 인증 | 교통카드 단말기, 하차벨, 버스·지하철 내부 노선도 중 하나 촬영. Vision `transit_boarding = true` |
| 하차 인증 | 정류장 표지판 또는 역명판 촬영. Vision `transit_stop = true` |
| 시간 조건 | 하차 촬영 − 승차 촬영 **≥ 5분** |
| 거리 조건 | 두 촬영 지점 사이 직선거리 **≥ 1 km** (앱이 촬영 시점 위치를 함께 전송) |
| 성공 | 위 네 조건 모두 충족 |
| 실패(`success:false`) | 하차 인증 후 시간 또는 거리 미달 |
| 진행 중 | 승차 인증만 된 상태. 결과 API 호출 안 함. 당일 자정까지 유효 |

**세 정거장 환산 근거:** 시내버스 정류장 간격은 대략 400~600 m라 세 정거장이면 1.2 km 안팎입니다. GPS 오차와 노선 굴곡을 감안해 직선거리 1 km를 하한으로 둡니다. 정류장 수를 직접 세지 않는 이유는 회의 피드백대로 GPS로 정류장 단위 판정이 어렵기 때문입니다.

> **위치는 거리 계산에만 씁니다.** 앱이 보낸 좌표로 거리를 계산한 뒤 좌표 원본은 저장하지 않고 거리(m)만 남깁니다. 1주차 인터페이스 정의서의 "비식별 위치, 좌표 원본 금지" 원칙과 같습니다.

> 걸음 수(HW 가속도)는 회의에서 언급됐으나 대중교통 탑승 판정에는 쓰지 않습니다. 탑승 중에는 걸음이 거의 없어 판정 근거가 되지 않습니다. 탐사 기록(7주차)에 보조 데이터로 남깁니다.

## 3. 공통 규칙

### 결과 전송

```
POST /api/missions/{missionId}/result
{
  "userId": 1,
  "success": true,
  "confidence": 0.82,
  "reason": "LANDMARK_OK: 붉은 벽돌 교회 건물"
}
```

| 필드 | 규칙 |
| --- | --- |
| `missionId` | Context API가 주는 오늘 미션의 id. AI가 단계로 추측하지 않음 |
| `confidence` | 1·2단계 규칙 판정은 `1.0`, 3·4단계는 Vision 신뢰도 (4단계는 두 사진 중 낮은 값) |
| `reason` | `코드: 설명` 형식. 코드는 아래 표. 로그·회귀 테스트용이며 사용자에게 보이지 않음 |

| 코드 | 의미 |
| --- | --- |
| `MOOD_OK` / `MOOD_NONE` | 1단계 기분 표현 있음 / 없음 |
| `WEATHER_MATCH` / `WEATHER_NEAR` / `WEATHER_OPPOSITE` / `WEATHER_NONE` / `WEATHER_API_DOWN` | 2단계 |
| `LANDMARK_OK` / `LANDMARK_INDOOR` / `LANDMARK_SUBJECT` / `LANDMARK_PEOPLE` / `LANDMARK_LOW_CONF` | 3단계 |
| `TRANSIT_OK` / `TRANSIT_TIME` / `TRANSIT_DISTANCE` / `TRANSIT_PHOTO` | 4단계 |

### 실패와 보류

- **`success:false` 는 "실패"가 아니라 "아직"입니다.** 백엔드는 상태를 `IN_PROGRESS`로 유지하므로 같은 날 다시 시도할 수 있습니다. 오빗은 재시도 문형을 씁니다(`docs/mission-context-injection.md` 4-4).
- **거부는 결과 API를 호출하지 않습니다.** 예외 대화 1번으로 응대하고 미션은 그대로 둡니다. 다음날 같은 단계 미션이 다시 배정됩니다.
- 기획의 "3회 이상 거부 시 심리상담 서비스 연결"은 회의에서 시간이 남을 때 추가하기로 했습니다. 구현 시 거부 횟수는 백엔드 `characters.refusalCount`(09-17 안건 5 제안)에 둡니다.

### 하루 시도 횟수

Gemini 무료 티어가 일 20요청입니다(4주차 확인). 대화와 Vision 판정이 같은 한도를 씁니다.

| 단계 | 하루 판정 상한 | 이유 |
| --- | --- | --- |
| 1, 2 | 제한 없음 | 규칙 판정이라 Gemini를 추가로 쓰지 않음 |
| 3 | 5회 | Vision 1회 = 요청 1회 |
| 4 | 승차·하차 각 3회 | 2장이 필요 |

상한에 닿으면 오빗이 "오늘 관측 장비 과열, 내일 재시도"류의 대사로 안내합니다.

### HW 반응 (09-17 공통 제어 코드 기준)

HW 코드(`hw/Orbit/Orbit.ino` `applyHardwareAction`)가 실제로 처리하는 값만 씁니다.

| 상황 | `oled` | `led` | `vibe` |
| --- | --- | --- | --- |
| 성공 | `EXPR_HAPPY` | `rainbow` | `strong_double` |
| `success:false` (재시도) | `EXPR_NORMAL` | `dim_blue` | `short_pulse` |
| 거부 (보류) | `EXPR_NORMAL` | `dim_blue` | `soft_continuous` |
| 판정 처리 중 (Vision 대기) | `EXPR_THINKING` | — | — |

> **HW 확인 필요:** `applyHardwareAction`의 OLED 분기에 `EXPR_HAPPY`가 없습니다. 지금은 성공 신호를 보내도 표정이 바뀌지 않습니다. 시리얼 `h` 테스트도 같은 이유로 표정 변화가 없습니다. 한 줄 추가로 해결됩니다.

## 4. 타 파트 요청 사항

| # | 요청 | 담당 | 이유 |
| --- | --- | --- | --- |
| 1 | Context API에 **오늘 미션** `{missionId, stage, missionType, status}` 포함 | 백엔드 | AI가 판정 대상과 `missionId`를 알아야 함 |
| 2 | Context API에 **날씨 범주** 포함, 또는 비식별 위치 제공 | 백엔드 | 2단계 판정 |
| 3 | 결과 API 요청에 `confidence`, `reason` 필드 추가 | 백엔드 | 판정 로그, 6주차 회귀 테스트 |
| 4 | 사진 업로드 경로 확정 (앱 → AI 서버 `multipart`: image, userId, captured_at, lat/lng) | 앱 · AI | 3·4단계. 카메라 촬영만 허용 |
| 5 | `applyHardwareAction`에 `EXPR_HAPPY` 분기 추가 | HW | 성공 표정 |
| 6 | 4단계 완료 후(최종 단계 성공 이후) 다음날 배정 정책 | 백엔드 · 전체 | 현재는 4단계 미션이 계속 재배정됨 |
